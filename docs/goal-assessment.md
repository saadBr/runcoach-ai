# Experimental goal assessment

## Purpose

The goal-assessment checkpoint provides an immediately usable bridge between descriptive
analytics and a future chronologically evaluated prediction model. It answers one question:
given the athlete's current training and verified same-distance personal best, what race-time
range is defensible enough to use for goal discussion?

The output is intentionally marked `experimental_not_validated`. It is not presented as a
validated machine-learning prediction and does not replace the performance-label audit.

## Evidence boundary

For each supported distance, the service compares:

- the most recent 42-day training block at the requested evidence cutoff; and
- the 42 days strictly before the athlete's verified PB at that same distance.

The comparison uses run frequency, total running distance, and distance-relevant longest-run
support. Longest runs are capped at 15 km for 5K, 24 km for 10K, 32 km for half marathon, and
42.195 km for marathon so an unusually long run does not dominate a shorter-distance result.

The components are weighted by target distance. Longer targets place more weight on long-run
durability. Ratios are clipped to 0.5 through 1.5 before aggregation so one extreme feature
cannot determine the result.

## Range policy

The support score selects a bounded range around the athlete's own same-distance PB:

| Support score | Optimistic bound | Conservative bound |
| --- | ---: | ---: |
| At least 1.10 | 98% of PB | 102% of PB |
| 0.90 to 1.10 | 99% of PB | 103% of PB |
| 0.75 to 0.90 | 100% of PB | 105% of PB |
| Below 0.75 or unavailable | 102% of PB | 108% of PB |

Training inactivity longer than 14 days shifts both bounds two percent slower. A stored form
index below -15 shifts both bounds one percent slower. These penalties are explicit and
testable rather than generated by an LLM.

Confidence is limited to `medium` even with complete evidence because this heuristic has not
passed chronological evaluation. It becomes `low` when the current or reference block has
fewer than six runs, support cannot be calculated, or current training is stale.

## Usage

With `RUNCOACH_ATHLETE_ID` configured and deterministic analytics already calculated:

```powershell
uv run python -m runcoach.cli.assess_goals
```

An explicit historical cutoff or one distance can be selected:

```powershell
uv run python -m runcoach.cli.assess_goals `
  --as-of-date '2026-08-27' `
  --distance 'half_marathon'
```

The command is read-only. It returns the range, confidence, both 42-day evidence blocks,
component ratios, a recommended training focus, algorithm version, and limitations.

## Path to the validated model and coach

This checkpoint is a visible product slice, not the final research method. The next steps are:

1. complete manual review of candidate performance labels;
2. evaluate training-feature models with chronological splits;
3. replace or calibrate this range policy only when held-out evidence supports the change;
4. expose the assessment through the API and dashboard; and
5. give the conversational coach a typed read-only tool for these results.

The language model may explain the stored evidence, ask about goals and constraints, and turn
validated outputs into understandable coaching guidance. Numeric race ranges remain produced
by versioned, tested code.

## Limitations

- The method assumes a prior verified PB exists for the target distance.
- It compares aggregate training support, not workout specificity or physiological response.
- It does not yet account for course, weather, illness, sleep, taper, or race execution.
- Four verified PB labels are not enough to claim a validated personalized prediction model.
- New activities beyond the database evidence cutoff cannot influence the assessment.
